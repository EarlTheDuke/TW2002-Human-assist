# Match-behind-flag switch test coverage

Test-only inventory of every fidelity switch named on a Match-behind-flag row. The grade is the every-row list in `docs/plans/gap-map-refresh-v6.md` (96 rows). `docs/plans/GAP_MAP.md` and `docs/plans/COMMANDER_NEXT.md` name the same switches, plus `QUASAR_ATM_ORDER_MODE` where GAP 7.4 says the shot order is Match-behind-flag, and `ATTACK_TURN_MODE` where the Commander mailbox names it on an R5 line. Game behavior and defaults were not changed.

A switch is covered when a test turns on the 3.11 setting and asserts the behavior written in those docs. For a helper in `V311_PROFILE_HELPERS`, `V311_PROFILE = "v311"` is that setting: the stored flag stays at its default, which is what the gap map means by behind a flag. Where the 3.11 value is already the stored default (`tw2002`, `keep`), the test is the one that asserts that default behavior and, when it is cheap, the legacy opposite.

Switches the v3.11 profile leaves off on purpose are still listed. Their adopted 3.11 behavior is the off path. The on path is coded, and a test sets it.

## Result

- Match-behind-flag rows in the v6 every-row list: 96
- Switches named on those rows (and the two extras above): 120
- Covered: 120
- New switch-literal tests this pass: 4, in `tests/test_mbf_switch_literals_v1.py` (`FED_TOW_LIMIT_MODE`, `FEDSAFE_FIGHTER_CAP_MODE`, `TAX_RULE_MODE`, `TRADE_IN_PARTS_MODE`). Older tests turned those four on only through `V311_PROFILE`.
- Could not test: 0
- Findings (a test saw code that does not match the documented 3.11 behavior): none

The other 116 switches already had a test that sets the 3.11 setting, or sets `V311_PROFILE` to `v311` and asserts the documented result, or asserts the stored default when that default is the 3.11 value. The four new tests set the switch itself, leave both profiles at `legacy`, and assert the documented number beside the legacy default. All four passed. Nothing was marked xfail.
